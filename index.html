What I built

Not managed at a distance — designed, written, tested and committed. The repositories below are public and every claim in this section is readable in them.

Infrastructure and governance, in code

  • A full Terraform stack for a cloud-watching service, applied plan-first — every change previewed and approved before it touches the account, with the provider pinned by lockfile.
  • An IAM role built as a NotAction deny-by-default: it permits an enumerated read set and denies everything outside it, including AWS actions that do not exist yet. The earlier version enumerated thirteen forbidden actions; I replaced it because a list of prohibitions is stale the day the provider ships one more service.
  • A runtime verifier in bash, shipped to the instance over SSM, that runs under the role itself and tries to mutate things. Written in bash rather than Python because installing a package onto the machine under audit would mutate the subject of the test.
  • No inbound admin access: no port 22, no key pair, Session Manager only. Budget measured on gross spend so credits cannot hide overspend.

A migration planner, engine and checker kept apart

  • An inventory contract that rejects any server depending on an ID absent from the inventory — written before the engine, with a negative test that goes red when the rule is disabled.
  • A dependency graph with cycle detection and topological wave layering, deterministic on tie-break so the same inventory always yields the same plan.
  • A rightsizing and TCO engine: cheapest instance type that is never smaller than the source, costed from a dated price catalog that carries its own provenance.
  • verify_waves — a checker that never regenerates the plan it judges, so it can check a plan drawn by people as readily as one the planner built. A checker that regenerates would only confirm the generator agrees with itself.
  • A converter from a real spreadsheet to the contract's shape that keeps only what resolves and names every value it drops.

Agents that read and cannot write

  • Read-only tool layers over real AWS data — cost, CloudWatch metrics, resource inventory. The critical ranking is derived in code, not left to the model, because a recommendation you cannot reproduce is not a recommendation.
  • An incident triage agent that ranks causes by severity × change-correlation and proposes a runbook step. It proposes; it never acts.
  • Eval harnesses with negative tests wired into CI: each check family has a deliberately corrupted artifact that must turn it red. A gate that can only pass is not a gate.
  • Consumption bounded in code before the API key ever entered CI — iteration cap, token accounting, budget cap. An unbounded loop with a credential in CI is an open invoice.
  • A fault-injection pilot: a real three-node chain on AWS with physically injected failures, so the ground truth came from an action outside the model's reach rather than from whoever scored the answers.

Stack: Python · bash · PowerShell · Terraform/HCL · AWS (IAM, EC2, SSM, CloudWatch, Cost Explorer, Budgets) · GitHub Actions · Jira + Confluence.

What I found

Building was the means. These are the conclusions, each one checkable and each one stated so that someone can disagree by pointing at data.

FindingWhy it holds
A spreadsheet holds a schedule; a graph holds an invariant. Benchmarked against a real 100-server estate and the four-wave plan drawn for it, the two orderings disagree on all 44 documented dependencies — because they optimise different things. The answer is not to replace one with the other: people keep owning the schedule, and a machine checks the invariant before anyone signs. The comparison is reproducible from the repo. The drawn plan encodes blast radius, team availability and change windows — none of which exist in an inventory, and all of which the tool is blind to.
Safety has to be structural, and structure has to be tested from inside. A policy is a claim until something tries to break it. terraform plan shows what was declared; only execution under the real principal shows what that principal can do. Verified from the account: 11/11 mutations denied · 0 inconclusive · 5/5 reads working. The verifier reports a third outcome — inconclusive — because its first version counted probes that died before authorization as passes.
The expensive defect is almost never in the model. In five of six projects it was in the instrument I built to measure the model, or in the sentence describing it. 25 defects raised and tracked, most caught before they could reach a published conclusion. Two corrections ran against my own interest and were published anyway.
Knowing when to stop is a deliverable. I closed a pilot without shipping it when I established that no incident in its corpus required the mechanism the pilot existed to test. Recorded as the project's outcome, with its evidence — not as a silence or a quiet pivot.
An agent finishes what has a computable stopping condition, and does not finish the questions asking what should be measured or where to invest. Held as a hypothesis with supporting evidence, not a finding — the experiment that would test it is scoped and has not been run. Stated as open on purpose. Calling it a finding would be the exact defect this portfolio catalogues.

What I do not claim

Stated here so nobody has to discover it.

  • No USD figure for LLM cost. That price file is verified: false. Token counts are publishable; dollars are not.
  • The migration cost figure is a list-price upper bound, not a costing. Any organisation running an estate that size pays negotiated rates, lower by an amount I do not know and will not estimate.
  • No saving is claimed from the planner. It computes the cost of a target, not a delta.
  • No conclusion about that migration's source records. What I retained is a sanitised, flattened extract. The dependency mapping lived in a system of record I no longer have access to, and nothing here is a statement about it.
  • No error attributed to the migration as it was delivered. The wave plan drawn at the time carries operational judgement the tool does not model and should not override.
  • No comparison against human analyst hours. The reference project never recorded how long the person took. It is the comparison everyone wants and the one that does not exist.
  • None of the six AI builds had a user other than me, and no before/after of anyone's work was measured. They answer “can you evaluate an AI solution honestly?” — the enterprise and consulting work above is where delivery to real customers lives.

How the work is run

Three standing rules, load-bearing rather than decorative:

  • Nothing exists if it is not in the tracker.
  • Every defect is raised as a defect, even when it is fixed on the spot — including the ones that make my own earlier claims look worse.
  • Nothing exists if it is not in version control, with the hash on the issue before anything is called done.

Roadmap, RAID register, decision log with trade-offs, definition of ready and done, and BPMN flows exist for the portfolio and can be walked through in an interview. They are not published because a personal tracker full of half-context is worse evidence than a conversation.
